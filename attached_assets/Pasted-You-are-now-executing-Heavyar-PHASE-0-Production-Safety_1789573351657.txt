C. FIRESTORE RULES BASELINE
==================================================

The audit found Firestore Rules are not tracked in the repository.

First, determine whether the currently deployed production rules can be retrieved safely using available Firebase tooling.

If they can be retrieved:
- preserve them
- compare them against actual application behavior
- migrate them into source control before changing them

If they cannot be retrieved:
DO NOT invent destructive rules blindly.

Instead:
- derive the minimum secure rules from actual current data models and application behavior
- validate using Firebase Emulator tests before any deployment

Add to source control as appropriate:

- firestore.rules
- firestore.indexes.json
- rule tests / emulator tests
- storage rules if Firebase Storage is actually used

Rules must enforce ownership and role restrictions independently of UI.

Critical requirements:

CUSTOMER / PROVIDER:
- cannot self-promote role
- cannot mark themselves verified
- cannot change another user's protected fields
- cannot arbitrarily modify financial fields
- cannot mark requests paid
- cannot force completion outside allowed lifecycle
- cannot read private information of unrelated users

REQUESTS:
Enforce allowed participants and valid lifecycle transitions.

Known lifecycle concepts include:

pending
accepted
in_progress
completion_requested
completed
cancelled/rejected where currently supported

Preserve the existing initiator-cannot-self-confirm logic.

CHAT:
Only request participants may access the request chat.

PUBLIC DATA:
Keep only intentionally public provider/equipment information readable publicly.

==================================================
D. SECURE CLOUDFLARE WORKER ENDPOINTS
==================================================

The audit identified unsafe Worker endpoints.

Implement Firebase ID token authentication for sensitive endpoints.

Build or reuse ONE shared server-side authentication helper.

For every sensitive Worker endpoint:

1. Read Authorization: Bearer <Firebase ID token>
2. Verify token server-side
3. Resolve the authenticated UID
4. Validate role / ownership / request participation
5. Reject unauthorized callers

Do not trust UID supplied in request body when the authenticated UID can be derived from the token.

--------------------------------------------------
PAYMENT CREATE ENDPOINT
--------------------------------------------------

The mobile client must NOT control the authoritative payment amount.

For create payment:

- authenticate the user
- validate they are the correct customer
- load the request server-side
- load required pricing data server-side
- calculate or verify the payable amount using trusted stored data
- reject arbitrary client amount overrides
- reject invalid request states
- prevent payment for another user's request

Do NOT redesign payment providers yet.

Keep Tap temporarily as the current provider.

--------------------------------------------------
PAYMENT VERIFY ENDPOINT
--------------------------------------------------

Verification must:

- authenticate the caller
- load the request
- confirm the caller owns/participates appropriately
- verify the charge directly with Tap
- confirm charge metadata belongs to the same Heavyar request
- never trust client-supplied payment result

The server must be the only authority allowed to mark payment state as paid.

--------------------------------------------------
CLOUDINARY DELETE
--------------------------------------------------

Do not allow arbitrary deletion by publicId.

Require authentication.

Before deletion:
- verify the authenticated user owns the associated equipment/media
OR
- verify an authorized admin action

Reject unrelated asset deletion attempts.

--------------------------------------------------
OTP
--------------------------------------------------

Improve the current OTP security baseline without building an unnecessary new authentication system.

At minimum:
- rate limit OTP requests
- limit verification attempts
- expire OTPs
- avoid logging OTP values
- avoid plaintext long-lived OTP persistence
- return generic responses that reduce account enumeration

If a durable backend store is required and existing architecture does not support it safely yet, implement the safest minimal solution and document it.
