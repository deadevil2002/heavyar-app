==================================================
PHASE 3 PRIMARY GOAL
==================================================

Build Heavyar's trusted identity-verification and risk-control foundation.

Heavyar is a Saudi marketplace for renting equipment and transactions may be high-value.

The system must support:

- customer identity verification
- provider identity verification
- future official Nafath integration
- manual verification components where legitimate
- verification requirements for sensitive transactions
- server-side risk policies
- admin verification operations
- trusted verification audit history

Do NOT fake Nafath integration.

Do NOT claim a user is Nafath-verified unless Heavyar has received and validated an official provider result.

Do NOT reverse engineer Nafath.

Do NOT implement unofficial Nafath APIs.

==================================================
1. CANONICAL TRUST MODEL
==================================================

Create a server-authoritative trust model.

Do NOT rely on a simple client-writable:

verified: true

Use structured backend-owned states.

Support at minimum:

unverified
pending
verified
rejected
expired
manual_review
restricted

Separate concepts clearly:

- identity verification
- provider/business verification
- account suspension
- risk/restriction state

A verified identity does NOT automatically remove an account suspension.

Normal clients must never be able to write trusted verification or risk state.

==================================================
2. VERIFICATION PROFILE
==================================================

Create a trusted verification profile for each user.

Design it so Heavyar can later support multiple verification components.

Example conceptual structure:

identity:
  status
  provider
  verifiedAt
  expiresAt

business:
  status

bankAccount:
  status

manualReview:
  status

overallTrust:
  status

Do not blindly use this exact schema if the existing architecture has a safer convention.

Provider overall verification must NOT become verified merely because one component passed.

Normal users may only read safe status information for their own verification attempts.

They must not read provider secrets or raw sensitive provider payloads.

==================================================
6. FUTURE OFFICIAL NAFATH FLOW
==================================================

The architecture must support this trusted flow:

1. User is authenticated in Heavyar.

2. User requests identity verification.

3. Heavyar backend creates an expiring verification attempt.

4. Heavyar backend communicates with official Nafath.

5. Nafath returns an official reference/correlation identifier.

6. User completes authorization through the official supported method.

7. Heavyar backend receives trusted status through official callback and/or polling.

8. Heavyar validates the official response.

9. Heavyar confirms that:
   - attempt exists
   - attempt belongs to correct UID
   - attempt is not expired
   - correlation ID matches
   - result has not already been consumed
   - provider result is valid

10. Heavyar updates trusted verification state.

The mobile client must never submit:

verified = true

as evidence of successful verification.

7. CALLBACK / REPLAY SECURITY
==================================================

Build callback-processing foundations with:

- provider validation
- correlation validation
- state transition validation
- attempt expiry validation
- replay prevention
- durable idempotency
- safe error responses
- append-only audit events

Where official Nafath signing/certificate validation is required, create the secure integration boundary for it.

Do not invent signing rules before official documentation is available.

==================================================
8. DATA MINIMIZATION
==================================================

Heavyar must minimize sensitive personal data.

Prefer storing only what is operationally necessary:

- provider name
- status
- attempt/reference ID
- timestamps
- minimal verification metadata
- expiry information if applicable

Do NOT store unnecessary:

- full identity documents
- full official response payloads
- secrets
- certificates
- PIN values
- authentication challenges

unless officially required and justified.

Never log sensitive identity payloads.

Create redaction helpers where necessary.

==================================================
12. TRUST / RISK ENGINE
==================================================

Build a conservative deterministic risk-policy engine.

Do NOT build AI-based fraud scoring in this phase.

Potential trusted signals may include:

- identity verification status
- provider verification state
- active suspension
- account age
- high-value transaction
- repeated verification failures
- repeated failed payments
- confirmed disputes
- confirmed complaints
- abnormal request behavior

Risk outcome should use a clear server-side result such as:

allow
require_verification
require_manual_review
restrict
block

Do not expose sensitive anti-fraud logic to clients.

Do not permanently suspend someone based solely on one automatic risk signal.

==================================================
13. TRANSACTION ENFORCEMENT
==================================================

Integrate verification/risk policy with the existing request and Phase 1 payment architecture.

When trusted policy requires identity verification:

the backend must reject progression to the protected action unless verification requirements are satisfied.

Possible protected actions may include:

- accepting high-value rental
- starting checkout
- creating payment
- sensitive provider actions

Do not rely on UI hiding.

Direct API calls must also be blocked.

Existing unaffected transactions must continue to work.
